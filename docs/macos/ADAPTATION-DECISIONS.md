# macOS 特性适配：分析与实现取舍

源码起点：`cf8bbed2d43526a9f6401d9e86de30bc12a56413`。本文记录已经实施的取舍，首批候选现已在本机安装；具体快照和限制见[安装验证](LOCAL-INSTALL-20260914.md)。需求状态见[当前适配清单](../common/MACOS-ADAPTATION-BACKLOG.md)，后续设计见[待批准方案](FEATURE-SYNC-PROPOSAL.md)。不能把本文已完成的首批工作视为全部特性已同步。

## 1. 筛选、快照、搜索与 CSV（D01、D03、D06）

**问题与现有基础。** `Main.swift` 的请求 ID 和后端 generation 已能拒绝大部分迟到回复；缺少的是“当前选中的范围”和“已显示结果”的绑定。范围请求失败时原图表、卡片与明细仍可能留下。CSV 则另发后端查询，无法保证搜索、排序与数据更新时间一致。

**Windows 参考。** `MainState.cs` 使用目录／缓存／查询身份、请求版本、已显示快照、导出序号和表格选择；请求期间可等待异步读取结束，再接受最新范围。

**macOS 选择。** 保留 URLSession 和现有请求取消逻辑，新增一个很小的 Foundation 状态对象记录身份、已显示快照与版本。选择新身份立即清空旧范围；失败保留待读取状态，使相同 generated_at 的后续健康响应也能触发重试。明细搜索和排序用同一函数生成显示行及导出行，保留 NSNumber 整数比较精度。

CSV 在用户选完保存路径时捕获快照，在后台准备同目录临时文件，回到主线程检查身份、快照版本和表格选择后原子替换。主线程保证检查与提交之间不会插入筛选回调，因此不需要照搬 Windows 的异步锁。失败或范围变化不覆盖原目标文件。

**验收重点。** A→B 的迟到结果、B 请求失败后的旧数值、相同后台时间戳重试、搜索／排序后导出、导出期间换目录、大整数和 CSV 引号／换行、未知与零的区别。

## 2. 设置保存（D04）

**问题与现有基础。** 当前设置写入先更新 UserDefaults，再发送后端请求，失败会回退。取消旧 HTTP 请求不能证明后端没有处理它；快速修改可能让较早的写入晚于新选择生效。

**Windows 参考。** `MainSettingsQueue` 合并待保存字典，串行发出请求，失败时以较新的字段覆盖较老批次。

**macOS 选择。** 当前这条后端接口只写刷新秒数，使用“一个正在写入值＋一个最新待写值”即可；不建立通用字典补丁框架。UserDefaults 保存用户最新意图；串行写后端，失败保留待写值并提供重试。重连后向新后端重新应用最新值。关闭保护必须覆盖主窗口红色关闭按钮、隐藏命令与应用退出，不能仅改一个按钮。

**验收重点。** A 写入时选择 B，A 成功／失败后只提交最新 B；后端重启后恢复；写入失败后保留选择；重试成功后清除待保存标记；未完成保存时不强行关闭主窗口。

## 3. 多预算草稿与保存确认（B01、B08）

**问题与现有基础。** macOS 已保存原始文本、日期及时分、原 revision；原来只有单草稿，编辑中外部导航被延后。后台出现更高 revision 也不能证明本次编辑已经保存，可能是另一条修改。

**Windows 参考。** 每个预算 ID 保存独立草稿、保留编辑起点 revision，并区分规则保存与后续设置／浮窗操作。

**macOS 选择。** 草稿仍归主窗口进程并保存在 UserDefaults，宿主继续独占预算文件写入。增加本平台 v2 草稿集合，保留 v1 `values` 字段格式和旧键作为迁移依据；不转换成 Windows 的 `fields` 格式。切换预算保存当前草稿，保存进行中才延后导航。明确的保存回复才确认成功；冲突可另存新预算，取消复制回到原选择。

损坏或超限草稿不得用空集合覆盖；原始字节先备份，用户才可重建。界面固定提交区，草稿保留、取消修改和另存新预算分别命名。

**验收重点。** 编辑 A→B→恢复 A；旧单草稿迁移；旧 revision 与对象删除；迟到保存回复；损坏／超限／写入失败；停用规则保存后仍停用；复制取消。

## 4. 预算配置损坏恢复（D05）

**问题与现有基础。** BudgetStore 已会拒绝写入损坏配置，但界面仍能进入无法成功的新建流程。

**Windows 参考。** 进入独立恢复状态，先备份原文件，再重建默认配置。

**macOS 选择。** 相同的用户结果，但只针对真实存在的预算 JSON 文件增加恢复命令。备份失败不清空，替换失败保留备份和原文件；恢复界面不显示普通创建流程。UserDefaults 不伪装成 Windows 的 JSON 设置文件，也不清空整个应用偏好域。

**验收重点。** 损坏文件仍拒绝普通写入；未确认恢复被拒；备份内容逐字节一致；成功恢复后可新建；备份或替换失败后仍有可恢复原件。

## 5. 两来源刷新与重试（D02）

**问题与 Windows 参考。** Windows 的 RefreshOperations 独立启动日志和账号查询，分别报告结果。macOS 原来已经能同时请求两者，但主面板代宿主刷新时还会再次调用包含账号查询的总刷新入口，难以提供明确的单来源重试。

**macOS 选择。** 保留现有采集器和 QuotaReader；把“手动刷新两者”拆成组合命令，底层各自提供日志刷新和额度刷新。复用采集完成、健康响应及额度组件的状态，发布紧凑状态到主窗口。浮窗、主面板和菜单栏共用同一更新状态窗口；账号开关直接控制 QuotaReader 的调度，单次重试不改变开关。

不增加采集任务或常驻进程。UI 明确区分日志快照时间、刷新进行中、错误，以及账号上次成功时间，不能把读取旧缓存的当前时刻标为新扫描成功时间。

**验收重点。** 任一来源失败不阻止另一来源；日志单独重试不触发账号请求；账号查询关闭时总刷新不启用它；关闭再启用时调度恢复；迟到跨数据目录状态不覆盖新来源。

## 6. 常驻入口与窗口关闭（U06、D04）

macOS 原来把“仅状态栏／仅浮窗”同时解释为关闭主面板，容易打断编辑。采用“常驻入口”和“主窗口”分别管理的语义：仅浮窗隐藏现有 NSStatusItem，仅菜单栏关闭浮窗，二者都保留主窗口；隐藏浮窗时保证菜单栏可恢复。保留同一 NSStatusItem 的注册与 autosaveName，不通过销毁重建改变位置。

关闭仍使用 NSApplication 的原生终止流程，但主窗口可在草稿写入失败或预算保存进行中拒绝。宿主先等待主窗口确认，再清理自身资源；拒绝或超时恢复可操作状态。快速重开的新意图不会被旧关闭回调覆盖。这比复用 Windows 的进程句柄、命名管道及强制终止路径更适合本平台。

## 7. 后续特性的分析边界

两来源更新状态将复用现有采集与 QuotaReader 的完成事件，不能通过重启额外服务获得状态。任务监控先明确日志事件、轮次身份、订阅和消息的归属，再选择 macOS 文件监听方式；不把新 Python 常驻进程作为默认方案。设置、菜单栏和浮窗按原生能力设计；动效与四边吸附在实现前单独检查过渡状态、命中区域及多屏坐标。

2026-09-14 已重新完成源码对比并查阅 Apple 官方与相关开源实现，详细取舍写入[待批准方案](FEATURE-SYNC-PROPOSAL.md)。任务监控、浮窗位置／贴边和统一设置仍未实施，等待本轮用户批准。
