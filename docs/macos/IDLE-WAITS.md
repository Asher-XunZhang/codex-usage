# 后端空闲等待优化

2026-09-14，源码起点 `cf8bbed2d43526a9f6401d9e86de30bc12a56413`，结果指当前工作区。首批界面与数据适配没有专项优化父进程监测；本次沿停止链路单独分析并修改。本文保存该专项的测量快照；随后已装入本机候选，见[安装验证](LOCAL-INSTALL-20260914.md)。

## 判断与依据

值得消除没有业务工作的周期超时，但不能据此认定旧版已明显耗电或卡顿。Apple 归档的[节能指南](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html)建议在应该闲置时每秒超过一次唤醒就调查原因，并建议无实际期限的等待采用事件通知。这是排查建议，不是耗电严重程度的硬阈值。

用户引用的 Windows 200 毫秒超时描述已不符合当前源码：`parent_watch.py` 已使用 `WaitForMultipleObjects` 同时等待父进程和停止事件，参数为 `INFINITE`。Microsoft [函数文档](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitformultipleobjects)确认这时仅在对象收到信号时返回。本次保留该实现及句柄生命周期。

## 逐项分析与修改

| 路径 | 修改前 | 当前工作区 | 取舍 |
| --- | --- | --- | --- |
| macOS 主面板父进程监测 | 立即首检，再每 0.5 秒检查 | `kqueue` 等待进程退出或停止管道，无周期超时 | 保留立即判断父进程的语义，避免调大间隔带来的退出延迟 |
| macOS 短时采集父进程监测 | 首先等待 0.2 秒，采集期间继续检查 | 复用同一原生等待 | 采集有界，原成本应按实际运行时间计算；复用已有机制即可同步减少超时 |
| macOS HTTP 主循环 | 每 0.25 秒超时检查停止标志 | 同时等待监听 socket 和停止管道 | 收到请求才处理；退出无需制造 HTTP 请求，也不在信号处理器内执行清理 |
| 共享索引刷新循环 | 每 0.25 秒检查，即使自动刷新关闭 | 自动刷新开启时等到下一次刷新期限；关闭时等待通知 | 复用已有 Condition；手动刷新、配置变化、停止均主动通知。两端共同生效 |
| Windows HTTP 与其他 Unix 父进程回退 | 各自既有超时／轮询 | 保持现状 | Windows HTTP 改造需要原生退出与控制接口实测，不将 macOS 管道套到 Windows |

macOS 使用标准库 `select.kqueue`、`selectors` 和 `os.pipe`，不引入第三方依赖、额外线程或常驻进程。Apple 的 [kevent 文档](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kevent.2.html)描述了 `EVFILT_PROC / NOTE_EXIT`；Python [select 文档](https://docs.python.org/3.12/library/select.html#kqueue-objects)确认 `timeout=None` 无限等待。

## 退出竞态与资源归属

- 注册前后都检查直接父 PID，避免父进程在检查和事件注册之间退出，或旧 PID 被其他进程复用；注册遇到 `ESRCH` 作为父进程已退出处理。
- 原生队列注册或等待出现其他错误会设置停止标志并报告异常，不能让后台工作失去监护后继续运行。
- 停止管道非阻塞，单向置位，不读取其中的字节，使父进程等待和 HTTP 等待都能观察到停止。预先停止、重复停止以及作用域结束后的迟到停止均可处理。
- 父进程线程只关闭自己的 kqueue；管道由外层作用域在 HTTP 循环结束且监测线程 join 后关闭。启动／join 被中断时，不提前关闭仍可能被借用的描述符。
- `SIGTERM`／`SIGINT` 仍设置停止状态；可读管道让被系统自动重启的等待返回，清理保留在主循环外。请求线程仍有原有超时及 daemon 生命周期。
- 停止同时通知刷新 Condition，唤醒扫描调度和等待刷新回执的请求；退出不会把尚未执行的刷新标记成已完成。扫描期间收到的新刷新请求仍需要下一次扫描。

在 macOS 26.5（25F71）、Apple Silicon、Python 3.9.6 上，使用空临时目录、随机 loopback 端口、自动刷新关闭，初次扫描完成后观察约 3.1 秒。每组分别启动基线和修改后进程，共三组；没有读取真实 Codex 记录或启动已安装 App。

| 指标 | 基线三组 | 修改后三组 |

超时返回由 Python 调用剖析记录，**不是整机唤醒次数**。CPU、停止耗时和峰值 RSS 仅是三个短样本的辅助观察，受调度、分配器和测量影响；不据此宣称稳定内存差额、耗电下降比例或电池续航收益。新增资源是有界的停止管道和内核队列，监测线程数量没有增加。

证据保存于 `build/reviews/macos-idle-waits/`：`compare_idle.py`、三份基线后端文件、`comparison.json` 和验证日志；这些是本机审查产物，不进入发行。GUI 的数据查询、实际自动刷新、额度请求和手动监督模式各有自己的活动，本文没有宣称整个 App 零唤醒。
