# 跨平台演进与兼容性

对齐用户可观察的能力和操作后果，允许各平台用合适的原生实现完成。单个平台的新设计不自动变成另一个平台的需求。

## 确定影响边界

- 比较实际目标分支与候选改动，覆盖已提交、未提交及未跟踪的依赖；记录用于结论的源码快照。不能仅凭目录名或“原生界面没改”断言没有影响。
- 分别判断平台界面、共享业务与协议、进程生命周期、构建及分发的影响。一次共享修改可能在另一平台改变错误路径或启动行为，即使主界面完全不变。
- 保留非目标平台已建立的行为，除非本次任务明确要求同步改变。复用共同业务语义，隔离平台资源管理；不要为消除代码差异强行统一系统习惯。
- 语言、依赖或框架的选择看原生能力、资源成本、可维护性与测试能力。性能优化先有可比较的测量，避免让一个平台为另一个平台承担无必要的常驻开销。

## 生命周期与接口

- 明确谁拥有后台任务、窗口、监听和持久化写入。打开、关闭、重开和退出应只影响各自负责的资源，不以重复宿主或重启常驻部分掩盖状态问题。
- 共享接口同时考虑正常与异常调用方、版本差异和退出中的迟到请求。新增本地控制能力仍需明确调用者边界；公开的实例标识不能自动当作授权秘密。
- 资源成本随实际活动变化；优先有所有者、可取消、有结束条件的工作。轮询频率依据响应需求与平台机制决定，不能把更频繁等同于更可靠。

## 验证与合入结论

- 选择受影响平台的对应检查。当前机器无法运行另一平台时，明确静态审查与本机验证的边界，并指出仍需验证的具体行为；不能将跳过算作通过。
- 发行是独立边界：检查实际包里的代码、依赖、资源和说明是否自洽。源码树中可运行，不代表打包后或解包后的开发材料仍完整。
- 使用可追溯的候选构建；不要覆盖正在使用或由其他任务维护的产物来做试验。安装与界面验证应能对应到同一份代码。
- 回答“是否影响另一平台”时分别给出直接变更、共享间接影响和未验证部分。新版本源码的影响与已安装旧版本的行为分开说明，避免绝对保证。

从 [文档导航](../../../docs/README.md)选择适用平台的架构与构建入口，已知差异和迁移目标见 [两端对齐清单](../../../docs/common/WINDOWS-MACOS-ALIGNMENT.md)。这些材料是定位入口；合入判断应重新核对当前差异，不能复用旧版审查结论。
