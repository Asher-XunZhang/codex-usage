# 高效开发与可验证交付

以减少返工和等待来提高速度：先消除影响方案的关键不确定性，再完成最短的可验证实现路径。

## 开始与推进

- 先确认用户要获得的行为、已有授权和本次不涉及的范围。小任务直接实现；只有较大或尚未确定的任务才需要单独方案文档。
- 从入口追踪到状态、数据和副作用，优先阅读将修改的调用链及现有测试。保留工作区已有改动，区分本次工作与并行开发，避免每次重新全仓审计。
- 已确认方案继续执行。只有缺失信息会改变产品后果、范围或不可逆动作时才澄清；优先把可独立完成的部分做成可评审结果。
- 先打通一个完整用户行为，再扩展相邻场景。复用现有状态和组件；只有当前需求确实需要时才抽象或替换技术，不夹带无关重构。
- 当本次会话允许并行 agent 时，将独立调查或互不冲突的模块分开；共享文件、构建目录及安装产物由一个执行者负责。并行工作应减少等待，而不是重复审查。

## 选择验证

围绕改动可能破坏的行为选择证据，而不是固定执行所有检查。

| 改动类型 | 优先验证 |
| --- | --- |
| 文档、文案、局部样式 | 链接与内容核对；影响可见布局时查看实际渲染 |
| 状态或数据逻辑 | 能复现问题的行为测试，以及相关失败、重试或逆向操作 |
| 交互或布局 | 原生界面中的操作结果；相关主题、尺寸、输入方式和过渡状态 |
| 共享接口、生命周期或发行链 | 直接调用方、受影响平台及实际产物的对应检查 |

- 优先使用现有测试入口。新增测试应能区分正确与错误行为，不以复述实现或增加数量为目标；低影响修改不强制新增测试。
- 必要检查通过后继续交付；只在新改动、失败或未消除的风险需要时扩大或重复验证。
- 判断性能改进时，在相同负载与生命周期阶段比较响应、CPU、内存和后台活动；不要用单次读数推断原因，也不要用牺牲行为正确性换取表面指标。

## 交付证据

- 实操前确认运行的程序来自本次候选源码。构建成功、离屏绘制、模拟事件与真实桌面操作分别说明；未执行的平台或操作不能计为通过。
- 用隔离数据验证写入和恢复，避免污染真实配置、预算与历史记录。用户要求不打扰时先做后台检查，明确尚未完成的前台验证。
- 结果简洁说明改变了什么、为何需要、验证了什么及剩余限制。修改行为时同步必要文档，不复制整份开发日志。

需要命令和历史证据时，从 [文档导航](../../../docs/README.md)选择适用平台的构建说明与验收记录，再核对当前脚本参数。历史记录用于定位检查方式，不能替代本次证据。
